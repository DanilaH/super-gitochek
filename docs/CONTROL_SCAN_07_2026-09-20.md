Три **новых узких** запроса, `in:name,description`: incremental — **10/10** новые уникальные кандидаты, fishing — **16/16**, mining — **8/8**; итого **34** новых уникальных ID. Это новые для реестра карточки, а не 34 подтверждённые механики. В `new.json` на данный момент оказались только три из этой группы: `Kumaken/DiggettyClicker`, `berkaycit/smashloop`, `shaocloud/miner-game`; остальные **31** ещё ожидают инспекции. Старые широкие README-запросы по тем же темам дали соответственно **4, 6 и 5** дополнительных кандидатов на 30 позиций каждый; напрямую сравнивать доли **нельзя**: их курсоры и история уже накопленной дедупликации отличаются от новых запросов. Не использовать это как статистически доказанный lift.

Сигнал об узких запросах подтверждён **по охвату новых ID** в штатном прогоне; по выходу *интересных кодово подтверждённых механик на час/запрос* полноценная проверка остаётся незавершённой, потому что 31/34 ещё не инспектирован и не просмотрен вручную.

## Вывод и следующий ограниченный эксперимент

1. **Оставить три узких запроса** вместе со старыми README-запросами; это подтверждённый прирост охвата с сохранением канала обнаружения сборников. Не называть его доказанным приростом качества.
2. **Не запускать сейчас ещё один массовый скан**: очередь уже 236. Приоритет — проверить 31 ожидающий кандидат трёх узких запросов, ограничившись README и 1–2 ключевыми игровыми файлами на перспективный проект. Отдельно фиксировать `confirmed mechanic`, `template`, `unfinished`, `unknown`, ссылку на код и примерный production burden. Если нет данных — `unknown`, не «готовая игра».
3. **Следующее изменение кода — только при подтверждённой отдаче:** дешёвое выявление шаблонов, discontinuation и настоящей игровой сцены. Переименовать автоматическую категорию `game` в `game_candidate` либо как минимум выделить `game_verified=false`; не делать массовый LLM-анализ каждого файла и не создавать сложный многоступенчатый пайплайн заранее.
4. **Один кандидат для прицельного live-playtest:** `Crystal Clicker` как референс малого односценного цикла «атакуй или ремонтируй». Сначала проверить ощущения, продолжительность и награды; если слабовато — не производить игру по инерции. `Smashloop` — запасной визуальный референс, а не автоматическое решение начать ещё один проект.

Вердикт по цели эксперимента: исправления курсора работают в штатном скане, узкие запросы расширяют покрытие, **доказательств повышения качества найденных игр пока недостаточно**. Основной bottleneck теперь не поиск новых ID, а ручная верификация уже обнаруженных проектов.
